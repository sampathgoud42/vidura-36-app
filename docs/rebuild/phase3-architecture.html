Architecture

Module boundaries, the conceptual and physical model with an evidence table, and — because you asked for it explicitly — an execution-safety design that makes duplicate orders and unwatched stop-losses structurally impossible rather than merely unlikely.

Found while designing the risk layer · verify before the next live session

Right now, if the API process stops, every open position keeps its take-profit and loses its stop-loss.

The take-profit is a GTC limit order resting on Tradier. It survives anything that happens to this application. The stop-loss is not an order at all — it is a threshold stored in a row, compared against the bid by a Python loop inside the API process main.py:325 _tradier_loop. The loop's own docstring says it plainly: "its cadence IS the stop's reaction time."

So a crash, a deploy, a restart, or an unhandled exception in that task leaves live options positions with unlimited downside and an armed profit-taker. Nothing on the venue would stop them out. Nothing tells the operator this has happened.

Three narrower gaps in the same mechanism: the loop sleeps 15 seconds before its first pass, so every restart has a 15–25 second blind window; the per-tenant lock is an in-process threading.Lock tradier_bot.py:62, which two uvicorn processes silently do not share — and main.py:84 exists precisely because two once ran at the same time; and place_option_order tradier_client.py:219 only implements limit and market, so nothing today could rest a stop on the venue even if it wanted to.

This is not a refactoring artefact — it is the current production behaviour, and it is the single most consequential thing I have found. The design below treats it as the primary requirement.

Your new mandate

Execution safety

You asked for proper stop-loss validation, double confirmation on buy and sell, and no duplicates — checking existing positions and waiting before acting. I have made that the centre of the architecture rather than a checklist bolted to it. Two principles decide every detail:

Principle 1 — structural, not procedural A duplicate order must be impossible to express, not merely unlikely to occur. Check-then-act is a race; a uniqueness constraint is a guarantee. Every guard below is a constraint or a lease, and the "wait and re-check" steps sit on top of that as confirmation, never as the primary defence.

Principle 2 — a stop must survive its watcher Any risk control that only exists inside a running process is not a risk control. It is a hope with a cron job.

The entry path, as designed

Today open_position tradier_bot.py:266 validates the side, the percentage, the sizing and the contract pick — and then places a real order with no check for an existing position, no check for a working order, and no idempotency key. A double-tap, or a mobile retry after the 60-second client timeout, buys twice. Note the asymmetry: the exit path is carefully defended — _place_tp asks the account what is already resting and refuses to rest more sells than the account holds. The entry path has none of that. Seven guards replace it:

1
Idempotency key, enforced by the database

Every execution request carries a key the client generates once per operator gesture. execution_attempt has UNIQUE(tenant_id, idempotency_key). The row is written before the venue is called; a second submit hits the constraint and returns the first attempt's outcome instead of placing an order.

Clients that send no key get a server-derived one: a fingerprint of tenant, contract, side, quantity and a short time bucket. A double-tap produces an identical fingerprint, so retries are absorbed even from a caller that was never updated.

2
A cross-process lease, because a threading lock is not one

The critical section is held under a row in execution_lease, keyed on (tenant_id, occ_symbol, venue), taken inside a BEGIN IMMEDIATE transaction with an expiry. SQLite in WAL mode admits exactly one writer, so this is a genuine mutex across every process on this machine — which the current threading.Lock is not.

Stated limit: this holds for one machine sharing one database file. It does not hold across machines, and it does not hold if the file is on a network share. Both are out of scope today; both would need Postgres, and that is the same conversation as Phase 0 Decision 1.

3
Check existing positions — the check you asked for

Inside the lease: refuse if this tenant already holds a pending or open position on the same contract and venue. The refusal names the existing position and its status, so the answer is "you already have this, here it is" rather than a bare error.

Adding deliberately to a position stays possible, but only by explicitly asking. The default answers no.

4
Ask the venue too, not just our own records

Our database can be wrong — an order can land while the write that records it fails. So the venue is asked whether a working buy_to_open already exists for this contract. This is the same argument _place_tp already makes for sells, applied to buys: trust the account, not our stored id.

5
Settle, then confirm — the "wait a few seconds" step

After placing, wait a short settle interval and re-read the venue's working orders for that contract. Exactly one is expected. If two appear, the extra is cancelled immediately, the position is marked for review, and the event is logged at warning level with both order ids.

This is confirmation, not protection — guards 1 and 2 are what prevent the duplicate. This is what catches the case they cannot see, which is an order placed by something outside this application.

6
Pre-trade risk validation, refusing rather than clamping

Before anything reaches the venue: take-profit must be strictly above entry and stop strictly below; both percentages inside configured bounds; the computed stop price must be greater than zero (a 100% stop is not a stop); expiration must not be in the past; a 0DTE entry must be before the cutoff — re-checked at the order, not only when the request arrived; and contracts must be a positive integer inside the tenant's per-order and per-day caps.

Every failure refuses with the arithmetic that produced it. Nothing is silently clamped to a legal value — a clamped stop is a stop the operator did not choose.

7
No entry while the stop cannot be watched

The risk monitor writes a heartbeat per tenant on every pass. If the last successful pass is older than a threshold, new entries are refused and the desk shows it. Opening a position whose stop-loss nobody is watching is worse than not trading.

This is the guard that would have made the alarm at the top of this page visible instead of silent.

The exit path

The existing sell-side logic is genuinely good and I am keeping its rules intact: cancel the resting take-profit before selling; never rest more sells than the account holds; before re-arming a cancelled order, check whether the position is gone too, because a sell that filled unseen looks identical. What changes is that these run under the same lease and idempotency machinery as entries, so the desk's sweep button and the background loop can no longer interleave — today they are serialised only by an in-process lock.

Signal  (no tenant — market data, identical for every operator)

Natural keys. A tenant is identified by slug; a position by (tenant, venue_order_id); a bot trade by (tenant, bot_key, external_id) — the same deterministic id the current ingest already uses for idempotency; a signal by (book, external_id). Surrogate integer primary keys everywhere, with the natural key as a unique constraint, because natural keys here are long strings that would bloat every foreign key.

Signal carries no tenant. Stated as an assumption in Phase 2 and worth repeating, because it is the one table that breaks the tenant-everywhere rule: super-research signals are market data, identical for everyone, and nothing in the code or the spec scopes them per operator. The repository base class therefore takes an explicit, greppable opt-out for exactly this table rather than silently permitting unscoped reads.

Passwords are hashed, credentials are encrypted — the asymmetry is deliberate

You asked for the .sam password to move into the database encrypted. It moves into the database, but hashed with Argon2id rather than encrypted, and the distinction is not pedantry. Encryption is reversible by design: anyone holding the master key — or a leaked backup plus a leaked key — recovers every operator's password in plaintext. A venue API key must be reversible, because the system has to present it to Tradier and Kalshi; that is exactly why tenant_credential uses envelope encryption. A login password never needs reading back, only comparing, so a slow salted hash is strictly stronger and takes the master key out of the blast radius entirely.

Your actual requirement — no plaintext password sitting in customers/<name>/.sam — is met either way. This way it is also met if the database leaks. If you want reversible encryption regardless, say so and I will build it, but I would be arguing against it in the runbook.

Wellness data is special-category personal data

Ethnicity, gender, diet and health goals are treated as sensitive under every privacy regime that matters. The table therefore inherits the credential handling rules from P2 S-2: never logged, never in an error message, never in a support export, excluded from any diagnostic dump. It is tenant-scoped like everything else, so the Phase 6 isolation tests cover it for free — but I am naming it because it is the one table where a leak is a privacy incident rather than a financial one.

Deliberately absent

No soft deletes, no generic audit table, no entity-attribute-value store, no lookup tables for fixed enums. tenant_secret_audit is the one audit table and it exists because the brief requires recording who changed a credential — not because audit tables are good practice in the abstract. Status values are CHECK constraints, not foreign keys to a two-row table.

One decision I will not take alone

The venue-resting stop. Everything else in this document I have decided, per your mandate. This one adds new integration to the order path — a bracket order pairing the take-profit with a stop on Tradier — and a stop that rests wrongly is its own kind of accident. It is also the only layer that actually closes the hole described at the top of this page.

My recommendation is to build it, prove it against the sandbox with a test that asserts both legs rest and that filling one cancels the other, and ship it behind a flag that defaults on for live and off for sandbox until you have watched it work. Say the word and it goes in the Phase 4 API design; say no and the monitored stop plus the heartbeat block is what you get, with the residual risk written into the runbook.

Meanwhile, separately from this rebuild: if you are running live positions today, the gap at the top of this page is real right now. The cheapest interim mitigation is not to leave positions open across a restart.
