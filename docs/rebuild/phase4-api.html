Method

The rules I applied

The brief is explicit that the goal is eliminating duplicate and incidental endpoints, not minimising the count, and that a coarse endpoint with a mode flag is worse than two clean ones. So merges happen only where the operation is genuinely identical and the difference is a value, not a behaviour. Three candidates that look mergeable are deliberately left alone, and I have said why for each — that list matters as much as the merges.

Deliberately not merged

Looks mergeableWhy it is not
/desk36/dmi + /tradier/hot Both return DMI, and Phase 1 proved they share _scan_symbol verbatim. But one takes an arbitrary symbol list ungated and the other sweeps a fixed universe through gates, and their response shapes differ. The duplication is in the code, not the API — the fix is one indicator module with two callers, which is what Phase 3 does. Merging the endpoints would need a mode flag, which is the anti-pattern the brief names.
/bots/commodities/signals + /desk36/dmi Different engine entirely: commodity signals wrap runtime/indicators/commodity_dmi.py over yfinance futures commodity_signals.py:1; the DMI board uses Tradier equity bars. Same indicator name, different data, different instruments. Merging them would be a genuine behaviour change.
/tradier/hot + /tradier/flow + /tradier/commodities All three are "read a background-swept snapshot" with live and refresh. The shape rhymes; the content does not. A single /scan?kind= endpoint would be one handler branching three ways — worse for testing, authorisation and caching, exactly as the brief warns.
The success criterion

A new bot needs zero new endpoints

Before — adding a bot family meant a new route block:
  /bots/<family>/status  start  stop  logs  trades  sync  processes  kill   ~9 endpoints
  plus a KEYS tuple, validators, a bot_manager env mapper, an ingest switch arm,
  ~9 client wrappers and a UI panel.                          6 files

After — the routes already exist and are keyed:
  GET  /bots                        lists the registry, now including the new bot
  GET  /bots/{bot_key}/status       works immediately
  POST /bots/{bot_key}/start        options validated against the bot's declared schema
  ...                               all eight, unchanged

What the author of a new bot writes:
  1. one config entry            key, name, category, versions, launch style, options schema
  2. one adapter class           lifecycle hooks + record mapping, conforming to the interface
  3. nothing else                discovery is automatic from the config

  0 endpoints.  0 migrations.  0 shared-library edits.  0 switch statements.  0 frontend changes.

The launch form renders itself from GET /bots/{bot_key}/config, which is why generalising that endpoint mattered more than its single current caller suggests. Phase 6 proves this by onboarding a throwaway bot as a test fixture and asserting no file outside the allowed list was touched.

The part that must not break

Frontend impact — exact, measured

Measured across frontend/src 116 lines reference user_id, across 5 files: viduraApi.js (46), BotStationSite.jsx (29), TradierSite.jsx (22), Desk36Site.jsx (18), WorldGate.jsx (1). 32 of 96 client functions take a user id, called from 41 sites across the three screens.

Those numbers look alarming and the diff is not, because of where the boundary falls. The brief requires the frontend change to be network layer only, and that is achievable exactly:

Change set A — ships with the backend, one file
  frontend/src/shared/viduraApi.js
    - 32 wrappers stop putting user_id in params/body   (they keep their signature)
    - ensureUser() is replaced by a call to /auth/me     (kills ?operator= and GET /users)
    - operatorName() is deleted                          (the hardcoded 'sampath' default)
    - 4 execution wrappers add an Idempotency-Key header
    - bot wrappers collapse onto /bots/{bot_key}/...
  Screens change: 0 files, 0 lines.
  They keep passing user.user_id; the wrapper simply no longer sends it.

Change set B — Phase 9 cleanup, after the tests are green
  Remove the now-unused parameter from 32 wrappers and 41 call sites
  across the three screens. Pure dead-argument removal, no behaviour.

Splitting it this way means the risky change (identity moves to the session) lands with a one-file frontend diff that is trivially reviewable, and the cosmetic change lands later where a mistake costs nothing. Doing both at once would put a 41-site edit in the same commit as the security fix, and I would rather not review those together.

Two user-visible effects, both approved, both stated plainly

  • One fewer round trip on load. Folding /worlds into /auth/me removes a request. The brief counts round-trip changes as potentially user-visible, so I am naming it: the desk will reach first paint marginally sooner. Nothing renders differently.
  • A double-tap on BUY now returns the first order instead of placing a second. This is the change you asked for. It is user-visible in the sense that the second tap now shows the existing order rather than a new one — which is the point.

One deletion I want confirmed rather than assumed

POST /users/{user_id}/verify-password has no reference anywhere in frontend/src, and its own docstring calls it a "legacy wellness/sports app login contract". That phrasing is my concern: it suggests a caller outside this repository. Sampath's folder also contains wellness-profile.json, which is consistent with another app having existed. The brief warns that frontends call things grep cannot see, so I am not deleting this on my own evidence. If a wellness or sports app still authenticates against it, deleting it breaks that app's login; if nothing does, it is an unthrottled password oracle and should go today.
