Tenancy Model

What a tenant is in this system, how a request resolves to one, and why nothing in the codebase today prevents one operator from trading another operator's account.

Verdict

A tenant is an individual operator. The evidence is unambiguous — no organisation layer exists anywhere in the schema, the API, or the credential layout. Q1 does not need to stop and ask.

The system has no tenant isolation. Not weak isolation — none. The identity a request acts as is a caller-supplied parameter, and no code path anywhere compares it to the authenticated session. Any operator who can sign in can read any other operator's ledger and place live orders against their broker account by changing one query string value.

The good news is in the frontend: it always sends the logged-in user's own id, on every call, without exception. So deriving identity from the session server-side instead of from the parameter produces byte-identical results for every real user — the fix is fully compatible with constraint #1.

Question 1

What a tenant is

Decision One operator = one tenant. There is no B2B organisation above the user. Each operator supplies their own Kalshi and Tradier credentials and is billed by those venues directly.

Four independent pieces of evidence agree, and none contradict:

The user table has no tenant columnbackend/app/models/user.py:22–36

User carries user_id, username, email, user_root_folder, timestamps. No org_id, no account_id, no role. Both relationships (trades, bot_runs) hang directly off the user.

Credentials are stored one folder per personcustomers/<username>/

Four folders exist — _test, sampath, sams, suma — each holding its own .env (Kalshi + Tradier keys), kalshi_private.pem, and .sam password. The unit that owns credentials is the person, not a company.

The password lives beside the credentials, per personbackend/app/api/v1/auth.py:1–12

The module docstring states it outright: adding an operator is "drop a folder under customers/ with a .sam and the broker keys in it, and register the user." One folder, one login, one credential set.

Entitlements are keyed by usernameworlds.json

users.sampath.worlds grants world access per operator, with a defaults block for everyone else. Its own comment calls them "operators". No grouping construct exists.

What this rules out

Schema-per-tenant and database-per-tenant are both wrong here. Tenants are individuals who sign up, so their count grows without bound and their lifecycle is runtime, not release. Any model where adding a tenant means a DDL statement fails the customer Onboarding Contract before it is written.

Question 3

Tenant propagation

Required It must be structurally impossible for a query to run without a tenant scope.
Found The opposite is the default. Omitting the parameter widens the query to every tenant.

Tenant scope is applied by a truthiness check, so a missing scope silently means "all tenants" rather than "refuse":

# services/trades.py:49–50 — and the identical shape at :69–70
stmt = select(Trade)
if user_id:
    stmt = stmt.where(Trade.user_id == user_id)
# user_id omitted -> every tenant's trades are returned, paginated

The same pattern governs bot runs at services/bot_manager.py:503–504. It is not accidental — api/v1/bots.py:51 documents it as intended behaviour, commenting "unscoped query: no single user's files to refresh". Roughly twenty endpoints declare user_id: str | None = Query(default=None), so unscoped is reachable by simply leaving the parameter off.

Two further escalation paths

Any caller can enumerate every tenantCriticalapi/v1/users.py:47–51

GET /users is behind authentication but not authorisation. It returns every operator's user_id, username, email and credential folder path — which is exactly the input needed to exploit Q2.

A new user can be pointed at an existing tenant's credentialsCriticalapi/v1/users.py:17–31, 59–67

_check_root_allowed verifies only that user_root_folder sits under customers_root. It does not verify the folder is unclaimed. POST /users with user_root_folder = customers/sampath creates a second identity that reads sampath's live Tradier token — no password needed, because the new row is used via Q2's parameter path, never via login.

Enforcement mechanism — and where SQLite changes the answer

The brief offers Postgres row-level security as the leading candidate. Your instruction to stay strictly on SQLite removes that option: SQLite has no row-level security, no policies, and no per-session SET app.tenant_id. That is a genuine loss and I want it on the record rather than quietly worked around — the database can no longer be the backstop, so enforcement moves entirely into application code.

What survives that constraint, and what I recommend, is a tenant-scoped session: the repository layer is reached only through an object constructed with a resolved tenant, and the base query builder injects the tenant_id predicate itself. A repository constructed without a tenant raises rather than returning rows. This is defended by three things working together — no model class is importable by request handlers directly, a single unscoped-query escape hatch that is explicit and greppable for the small number of genuine admin jobs, and the Phase 6 unscoped-query test asserting a hard failure.

Honest assessment: this is enforcement by construction, which is materially weaker than enforcement by the database. It holds as long as nobody adds a second path to the engine. Postgres would let the database refuse a leaking query even if the code asked for one. That trade is yours to make and it is Decision 1 below.

Splitting the user tables would have forced a duplicate identity per world.

Question 5

Blast radius

Stated plainly, as the brief requires.

If a single query is missing its tenant scope

On a read: one operator sees another's positions, ledger, P&L, bankroll and bot configuration. On a write or an execution path: an order is placed, modified or closed on another operator's real brokerage account, using that operator's live token, and it settles as a genuine financial transaction. There is no compensating control — no per-order ownership check, no confirmation step keyed to identity, no audit trail that would attribute it. The affected operator's first signal is a position they did not open.

What prevents it from reaching production today

Nothing. There is no tenant isolation test in the suite of 30 test files, no authorisation layer, and no review gate that would catch it. The three findings in Q2 and Q3 are in the running system now, not hypotheticals.

What will prevent it after the rebuild

  1. Identity is resolved once at the edge from the session and never read from a parameter — a request cannot express another tenant's id, so the attack has no input surface.
  2. The repository layer refuses to build a query without a resolved tenant, so a forgotten where clause is a crash, not a leak.
  3. Phase 6 tenant isolation tests are the highest-priority category in the suite, covering every read and write path, including ID-guessing returning not found rather than forbidden.
  4. The unscoped-query test asserts that a tenant-less query fails hard rather than returning everything — the precise inversion of if user_id:.

Decisions I need from you

01 SQLite removes the database-level tenancy backstop

You have asked for strictly SQLite. That is workable, and the single-schema model above is the right shape for it — but it means a leaking query is caught by application code and tests, never by the database. Postgres row-level security would refuse the query itself.

My recommendationProceed on SQLite as instructed. The tenant-scoped repository plus the Phase 6 isolation suite is a real defence, and this is a single-machine desk with four operators, not a public SaaS. I want the trade acknowledged rather than assumed. If the operator count is ever expected to grow beyond people you personally know, this decision should be revisited before that happens.

02 Flyway cannot be used on this stack

The brief mandates Flyway with a clean baseline. Flyway is a JVM tool and does not support SQLite; this is a Python/FastAPI/SQLAlchemy project with no JVM anywhere in it. The requirement cannot be met literally.

My recommendationUse Alembic and keep every property the brief actually wanted from Flyway: a clean baseline with the old history deleted, an explicit versioning scheme, ordered and repeatable migration from an empty database, and a Phase 6 test that migrates from empty and fails the build otherwise. I will hold Alembic to the Flyway contract. Adding a world will not require editing existing migrations.

03 The shared TBOT_API_KEY belongs to no tenant

It bypasses login entirely and can pass any user_id, so it is a permanent cross-tenant key. Once identity comes from the session, this key has no tenant to resolve to and every scoped endpoint must reject it.

My recommendationKeep it, but demote it to unscoped operational endpoints only — health, readiness, version. Anything touching tenant data requires a session. I need to know what currently uses it: if a cron job, a bot supervisor, or your deploy scripts authenticate with it against data endpoints, that breaks, and Phase 1 needs to inventory those callers before Phase 4 designs around it.

04 Scope of the sampath-only migration

You have said to use sampath as the customer for this migration. Three other folders exist: _test, sams, suma. sams and suma each hold real Kalshi keys and a sports trade history.

What I needConfirm which you mean: (a) build and validate the whole rebuild against sampath's data only, importing the others later by the same tested path, or (b) sampath is the only tenant that carries forward and the other three are dropped. These produce different Phase 8 work and different reconciliation targets. I will assume (a) unless you say otherwise, because it is the reversible one.

05 Fixing the tenancy hole is invisible — but I still want it acknowledged

Constraint #1 forbids user-visible change. Removing user_id from the wire and taking it from the session is invisible for every legitimate call, because the frontend already sends only its own id, always. The one behaviour that does change: unscoped calls stop returning all tenants' rows.

My readingThat is a security fix, not a UX change — no screen in the desk requests an unscoped list, and any that did was displaying other people's trades. I am treating it as approved-by-default under constraint #1 rather than as a deliberate behaviour change, but the brief says bugs are yours to decide, so I am listing it rather than fixing it silently.
