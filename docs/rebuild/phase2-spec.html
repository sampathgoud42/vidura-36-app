Behaviour

Workflows

Stated as rules. Where the current implementation has a rule I believe is wrong, it is marked and carried to the decision list rather than corrected here.

Trading domain

T-1Open a managed options position
Purpose
Turn "buy SPY calls in the 0.25–0.45 delta band with 50% of buying power" into a filled position with both exits armed.
Inputs
Tenant, symbol, side (call/put), delta band, buy %, take-profit %, stop-loss %, venue (sandbox default), optional expiration or 0DTE pin.
Outputs
A position row; a resting take-profit sell order on the venue; a monitored stop-loss.
Rules
  • The delta band is spoken as a magnitude but searched as a signed range: calls +min..+max, puts −max..−min. Matching on absolute value is wrong and recorded every put's entry delta as positive.
  • A contract with no live two-sided quote is never entered — an option that cannot be exited must not be opened.
  • Ties within the band break toward the tighter spread.
  • Size is floor((balance × buy_pct) / (price × 100)). The ×100 multiplier is mandatory; omitting it orders 100× the intended size.
  • Buy % is a target, not a cap. A tolerance band either side lets an indivisible contract that would otherwise size to zero still trade, and stops a partial lot leaving budget parked.
  • Entry limit is the mid-price when the spread is wide, the ask when it is one or two cents.
  • Take-profit rests on the venue so it survives an API restart. Stop-loss lives in the monitor loop and survives because the row does.
  • Exits arm only after a delay and after the holding is visible on the books — a fill report is not the same as a position, and selling into that gap is what the venue rejects.
  • Sandbox is the default for every call that does not name a venue. paper_only refuses a live request outright rather than silently downgrading it.
Errors
No contract in band → refuse with the band searched. Sizing below minimum → refuse with the arithmetic. Venue rejects → surface the venue's own message. Live requested while paper_only → refuse and say the server is locked.
T-2Close or sweep a position
Purpose
Exit one position, or flatten everything, without leaving an orphaned resting order.
Rules
  • Cancel the resting take-profit before selling. A sell that races its own TP double-sells.
  • Sell to close is a limit at mid when the spread exceeds two cents, market otherwise.
  • A forced close skips the arm-delay guard; that is what force means and it is the operator's explicit override.
Errors
Position already closed → report the terminal state, do not re-sell. Venue unreachable → the row stays open and reconciliation catches it later.
T-3Auto-trade: A/B signal into options
Purpose
Trade super-research signals automatically, without buying a premium that is already melting.
Rules
  • LONG signal → call, SHORT → put, on the signal's own ticker, from the desk's delta band.
  • The signal does not place the order. The chosen contract's bid is sampled for a minimum observation window and bought only while rising or stable.
  • A fading bid is not discarded — watching continues and the trade fires the moment a trailing window turns steady again, giving up at a maximum wait.
  • "Falling" includes a bid that spiked and gave the move back, not merely one that ended lower.
  • Expirations run today out to a maximum DTE. Same-day contracts are entered only before the 0DTE cutoff, checked twice — once so an observation that cannot finish in time never starts, and again at the order.
  • After an entry the ticker is on cooldown; later signals are ignored however good. The cooldown is read from the position ledger, not watcher memory, so it survives a restart, and it is re-checked at the order so two observations ripening together cannot both slip through.
  • Rejected buys do not start a cooldown — an order that never reached the book must not lock a ticker out.
T-4Auto-trade: opening-range level cross
Rules
  • A new cross above the 10-minute high is a call candidate; below the low, a put.
  • Only crosses stamped inside the configured CST window qualify.
  • A candidate waits a confirmation interval, then the snapshot is re-read: the trade fires only if that level's latest signal is still the same. A flip back inside the range cancels it.
  • Orders are pinned to today's expiration and sized by percentage of option buying power. Landing below the minimum skips the trade — recorded, not retried.
  • Each (date, ticker, level, bar) trades at most once; the watcher re-arms per CST date.
T-5Market data reads
Purpose
Quotes, option chains, timesales, DMI readings, options flow, hot scan.
Rules
  • Indicator maths lives in exactly one place. The DMI board and the hot scan differ only in universe and gating, never in computation.
  • Sweeps run in the background; a read returns whatever snapshot exists and never blocks on the venue.
  • Missing symbols are returned as null rows, not omitted — a dropped row looks like a rendering bug rather than "no reading yet".
  • Every read is cached with an explicit TTL, because a reading cannot change until the next bar closes.

Bot station domain

B-1Start a bot
Inputs
Tenant, bot key, version, per-bot bankroll, target %, stop %, contracts, and family-specific options.
Rules
  • One running instance per (tenant, bot). A second start is refused — a double-launch corrupted a live ledger once and must not be possible again.
  • Machine shutdown on halt is always forced off, whatever the bot's own default.
  • While the server is paper-only, every known dry-run flag is forced on and no live flag is honoured.
  • The subprocess environment never inherits credentials from the API process. Each bot loads its own tenant's credentials.
  • Bankroll and target are per bot, not per account. The venue account is shared across bots, so an account-wide floor let one bot's drawdown halt the others.
Errors
Already running → 409 with the existing run. Script missing → report the resolved path rather than a generic failure. Credentials unusable → refuse to launch, do not start a bot that cannot trade.
B-2Ingest bot trades into the ledger
Purpose
Mirror bot-owned trade records into one ledger so every family reports the same way.
Rules
  • Upsert on a deterministic external id — re-running must be idempotent.
  • Rows corrected by reconciliation are stamped and are never overwritten by a later ingest. Without that lock the next auto-sync reverts every correction to the bot's own estimate.
  • The original record is preserved verbatim alongside the mapped row.
  • A record whose live-or-paper status is genuinely unknown is stored as unknown. It is never guessed.
B-3Reconcile the ledger against the exchange
Purpose
The bots' own realised P&L is an estimate. A forensic pass found it overstated by roughly $8,000. The exchange's fills and settlements are what the account really did.
Rules
  • Pass 1 — settle stale opens. A row still open past a staleness floor: if the ticker is still an active position the bot is simply still in it, leave it. If not, it resolved — take true P&L from fills and settlements and close it.
  • Pass 2 — fee true-up. Closed live rows not yet priced from the exchange are recomputed so fees net out on both legs, and corrected when the booked figure differs.
  • Every fill is a cash outflow of count × side_price + fee; matched yes/no pairs redeem at $1; settlement revenue is added. The exchange records each fill as the token the account acquired, so a "sell yes" arrives as "no bought at 1−price".
  • That formula needs a market's whole fill history, so it applies only when one ledger row owns the ticker. Shared tickers fall back to per-leg arithmetic that is provably equivalent for yes-held rows only — no-held shared-ticker rows are skipped rather than mis-booked, because the inversion that would mis-book them shipped in every bot.
  • Reconciliation is a preview by default and applies only when asked.

Shared

S-1Sign in and act as a tenant
Rules
  • One message for "no such operator" and "wrong password" — the screen must not confirm who exists. Failures are counted per typed name so username guessing is throttled too.
  • Lockout after repeated failures; a fixed delay burned on every failure path so a missing operator is not detectable by response time.
  • The session determines which tenant the request acts as. Full stop. No request may name a tenant. This is the change that closes all five Phase 1 findings, and it makes four of them structurally unreachable rather than merely fixed.
  • Requesting a record belonging to another tenant returns not found, never forbidden — forbidden confirms the record exists.
  • A data query without a resolved tenant is a programming error and fails hard. It never widens to all tenants.
S-2Hold and use tenant credentials
Rules
  • Credentials are stored encrypted at rest with a per-record data key wrapped by a master key from the environment. The master key is the only credential material in any file.
  • Decrypt at the point of use, hold briefly, never log, never return in a response, never include in an error, a stack trace, a debug dump or a support export.
  • Rotation and revocation happen at runtime with no downtime, and record who changed what and when.
  • Adding a tenant is a runtime write. No file, no migration, no deploy, no restart.

Extension points and their onboarding contracts

Four extension points exist. For each: what it costs today, measured; and the contract I am asking you to hold me to.

1. A new bot — the primary success criterion

Contract — a new bot 1. one config entry declaring key, name, category, versions, launch style, and its options schema
2. one implementation class conforming to the bot adapter interface (lifecycle + record mapping)
3. zero registration lines — discovery is automatic from the config

Must not require editing any shared library · adding or changing any API endpoint · adding or changing any table or migration · editing any other bot's code · editing any dispatch switch · any frontend change

The endpoint half of that is achievable because the eight operations are already identical across families: status, start, stop, logs, trades, sync, processes, kill. Keyed by bot_key they become eight endpoints instead of thirty-seven. The family-specific options that differ become a declared schema per bot rather than a hand-written route. Phase 4 will put every one of those merges in the consolidation table with its user-visible-change column, and Phase 6 proves the contract by onboarding a throwaway bot as a fixture.

2. A new tenant

Contract — a new customer Three runtime writes: a tenant row, an encrypted credential record, a world-access record. Zero deploys, zero files, zero schema changes, zero restarts.

Today every one of those is violated: a folder, a .env, a .pem, a .sam, and an edit to worlds.json. You have said more customers are coming, so this contract is the one with a date attached.

3. A new research ticker

Today: copy eight files, six of them byte-identical, to change sixteen constants.

Contract — a new research ticker One config entry carrying the sixteen values that genuinely vary. Zero copied files.

4. A new world

Today a world is a frontend route plus a worlds.json key. Since the trading domain serves two worlds already and the backend has no world discriminator at all, this stays cheap — and the spec keeps it that way: a world is a presentation grouping, never a backend concept. Adding one must require zero backend endpoints and zero tables.

Decisions — behaviour I will not change silently

The brief says bugs are neither carried forward nor fixed without you. Eleven items. The first four are the security fixes; they are the only ones I would push back on if refused.

D1Tenant comes from the session, never from the requestSecurity

Removes user_id from every request. Kills the ?operator= switch, the parameter-swap attack, and the "new user pointed at an existing folder" escalation in one change.

ProposedAdopt. User-visible impact for sampath: none — the resolved id is identical. For any other operator: they stop seeing sampath's data, which is a bug being removed. Frontend diff required and it lands in the same change set (Phase 4 rule).
D2An unscoped query fails instead of returning every tenantSecurity

Inverts if user_id:. Any endpoint that today returns all tenants' rows when the parameter is omitted will instead refuse.

ProposedAdopt. No screen requests an unscoped list; any that did was displaying other operators' trades.
D3Delete the password-verification endpointSecurity

POST /users/{user_id}/verify-password is an unthrottled oracle against any operator's password, bypassing every defence /auth/login has. Nothing calls it. Its docstring calls it a "legacy wellness/sports app login contract".

ProposedDelete. I need you to confirm no external app outside this repo calls it — that is exactly the statically-invisible caller the brief warns about. If one does, it becomes a real login with real throttling.
D4Demote the shared API key to operational endpointsNo caller

Health, readiness, version only. Anything touching tenant data requires a session, because a shared key resolves to no tenant.

ProposedAdopt — evidence above shows nothing sends it today.
D5Trades of unknown mode are invisible in both ledgersUser-visible

A row with unknown live-or-paper status appears only under "all" — not under LIVE and not under PAPER. The intent is sound: a live ledger must never quietly include an unverified trade. But the same rule hides those rows from the paper ledger too, so 93 of sampath's v2 rows are in neither view and the two views do not sum to the whole.

Options(a) keep as-is; (b) show them in PAPER, since an unverified row is more likely paper than live — I do not recommend this, it launders unknowns into a category; (c) keep them out of both but surface a visible "N unclassified" count so the gap is honest rather than silent. I recommend (c): it changes what the user sees, so it needs your approval, but it fixes a ledger that currently under-reports without saying so.
D6Per-bot P&L is measured against an account-wide baselineCorrectness

A run records the account's value at launch. The venue account is shared across bots, so the delta is "what the account did while this bot ran", not "what this bot earned". The code's own docstring says this becomes "a P&L figure that quietly credits one bot with another's trades".

ProposedCompute per-bot P&L from that bot's own ledger rows and drop the account-baseline delta, or keep it but label it "account change during run". Either way the number on screen changes, so this is yours.
D7Three data mutations run on every bootDesign

database.py:63 recomputes India signal timestamps; :118 backfills btc15 modes; :171 rewrites every stored credential-folder path. All three are idempotent and each is well argued. But they are unversioned data migrations wearing the costume of startup code, they run forever, and one of them silently rewrites where credentials are read from.

ProposedConvert to versioned, run-once migrations. Keep the path-relocation behaviour but make it explicit and logged at start, not a silent UPDATE. Same outcomes, auditable.
D8Sessions are in-memory, so any restart signs everyone outOps

Deliberate and documented — a desk left running overnight cannot be walked up to. The cost is that a deploy during market hours signs out every operator, and this desk can hold open positions with monitored stop-losses.

ProposedKeep the behaviour; it is the right trade for a trading desk. But it becomes a documented precondition in deploy.md and safe-shutdown.md rather than folklore. Note the monitored stop-loss is the real exposure, not the sign-out — Phase 5's safe-shutdown doc must state what happens to a monitored SL across a restart, and I will need to verify that behaviour before writing it.
D9The v2 CSV's undeclared columnData

231 rows carry a 20th field the 19-column header never names; 93 rows predate it. Import must decide what the 93 are.

ProposedImport all 324. Map the 20th field to the mode flag for the 231. Leave the 93 explicitly unknown rather than inferring from run windows — the existing inference joins on time ranges and I do not trust it enough to stamp real-money rows with it. Ties to D5.
D10The main CSV is an event log, not a trade tableData

99 rows = 45 opens + 54 close events, joined only by ticker, and ticker is not unique across the file.

ProposedReconstruct trades by pairing each close event to the most recent unclosed open on the same ticker. Report every unpaired row rather than dropping it. Phase 8 delivers the counts in a dry run before anything is written.
D1137 client wrappers no screen callsCleanup

Whole families of them — every *Processes and *Kill, sportsPerformance, parleyActiveBets, the engine-gates pair.

ProposedNothing yet. Phase 4 lists them individually with evidence and Phase 9 deletes only what you confirm. I flag it here because if any of these is a half-finished feature you intend to finish, I should design for it now rather than delete it and rebuild it later.

Phase 8 must preserve login for sampath, so the new store hashes it on first successful login rather than guessing a hash format that was never used. I will confirm this against the file before writing the import, per the brief's instruction not to guess.
  3. runtime/ stays as vendored bot scripts. The rebuild replaces the backend around them, not the trading engines themselves — those are the strategies, not the plumbing, and rewriting them is not what you asked for.
