Correction · this section previously claimed a live bug

I reported a duplicate-sell bug here. It was test-order dependence, not a bug — retracted.

My first baseline run reported 3 failed, 373 passed, and two of the failures were in test_tradier.py asserting that a second monitor pass does not stack another sell (assert 2 == 1). I wrote that these run against a fake venue and were therefore deterministic, and concluded the guard did not hold in this build.

That conclusion was wrong. test_tradier.py passes 52 of 52 when run on its own, and two consecutive full-suite runs now report 375 passed, 1 failed. The two tests were failing because of state carried between tests in one session — module-level globals such as the per-user monitor locks and the process table persist across a run — not because the code places two sells.

I said "deterministic — no network, no timing, no flakiness" on the strength of the fake venue alone, without running the file in isolation to check. That was the step I skipped, and it is the step that would have caught it.

What still stands, on code rather than test evidence: the per-tenant lock is an in-process threading.Lock tradier_bot.py:62, so it genuinely does not span two uvicorn workers, and main.py:84 exists because two have run at once here. That is read directly from the source and is unaffected by this correction. The cross-process lease in Phase 3 is still the right fix — it is just not fixing a bug that is currently firing.

The remaining failure, test_gex0dte expecting 502 and getting 200, is vendor-dependent and unrelated.

Hygiene

Two things worth knowing about this working copy

Stale bytecode was making tracebacks lie Every traceback pointed at ..\tradier-bot\tests\… — a sibling project this repository was copied from. The copy brought __pycache__ with it, and compiled Python bakes in the absolute path of the file it was built from. I cleared all __pycache__ directories and .pytest_cache; the baseline above is from a clean run. Worth adding to .gitignore housekeeping, and worth knowing before anyone debugs a stack trace here.

Second: pyproject.toml still declares name = "tradier-bot". Cosmetic, but this project is vidura-36-app and the sibling still exists on disk at D:\_projects\tradier-bot. I have not touched either — flagging it so the two do not get confused during Phase 7, when one of them starts changing.
