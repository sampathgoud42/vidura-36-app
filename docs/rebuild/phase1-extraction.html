Correction to Phase 0

I reported that the frontend always sends the logged-in user's own id. That is wrong, and the truth is worse.

Every screen resolves its acting identity through ensureUser() viduraApi.js:157, which does not consult the session at all. It reads a username from operatorName() viduraApi.js:144 — taken from a ?operator= URL parameter, persisted to localStorage, defaulting to the hardcoded string 'sampath' — then looks that name up via GET /users and uses whatever id comes back.

So the identity the desk acts as is set by a URL parameter, not by who signed in. Sign in as any operator, append ?operator=sampath, and the desk trades sampath's account. And because the fallback is a hardcoded name rather than the session, an operator who is not sampath signing in today lands on sampath's data by default — the build sets no VITE_TRADIER_OPERATOR anywhere.

The Phase 0 conclusion still holds — moving identity to the session is correct and is invisible for sampath, who is the only operator this deployment resolves to. But it is not invisible for anyone else, and what changes for them is a bug being removed, not a feature.

VerdictHypothesis confirmed

Tradier Platform and 36 Trades are one domain with two clients. The counts the brief asked for: presentation differences 2, client-capability differences 0, genuine business rules 0. There is no drift to resolve because there is no forked logic — they were never forked, they share a client module and a service layer already.

Bot Station is a genuine domain boundary. Zero endpoint overlap with either of the other two, a different venue, different instruments, and subprocess execution semantics nothing else has.

Nothing here justifies a second schema, a second service layer, or a /config/thirty-six-trades. The Phase 5 layout stays at shared / trading / bot-station.

Authentication model

Two paths are open (/auth/login, /auth/status). Two accept a scoped push token and nothing else (/super/gex0dte/refresh, /heartbeat) — that one is genuinely well designed, and its comment explains why: a leaked push token poisons gamma data rather than placing an order. Everything else takes a session token or the shared TBOT_API_KEY, interchangeably.

Endpoints nothing calls

Two layers, and the distinction matters because the brief warns that frontends call things grep cannot see:

I am proposing no deletions yet. That is Phase 4's table and Phase 9's manifest, and both need your confirmation per endpoint.

Security

Tenancy findings, consolidated

Phase 0 found three. Extraction found two more, and one of them is the default path rather than an attack.

1. Acting identity comes from a URL parameterCriticalviduraApi.js:144,157

?operator=<name> selects which operator the desk acts as, persisted in localStorage, defaulting to a hardcoded 'sampath'. The session is never consulted. This is the correction above, and it is the most exploitable of the five because it needs no crafted request — just a query string.

2. Every data endpoint trusts a caller-supplied user_idCriticalapi/deps.py:10

No code path compares the session's user to the requested one. current_session is used by /auth/me and nothing else.

3. Omitting user_id widens the query to every tenantCriticalservices/trades.py:49

if user_id: — a missing scope means "all", not "refuse". Roughly 20 endpoints declare the parameter optional.

4. A new user can be pointed at an existing operator's credential folderCriticalapi/v1/users.py:17

_check_root_allowed checks the folder is under customers_root, never that it is unclaimed.

5. An unthrottled password oracle, new in this phaseCriticalapi/v1/kalshi.py:211

POST /users/{user_id}/verify-password takes any operator's id and a candidate password and answers 200 or 401. /auth/login is carefully defended — lockout after 10 failures, a burned second on every failure, one message for both failure modes. This endpoint has none of that, and it reaches the same .sam file. It is a login bypass for the throttling, and no screen calls it.

What the tests say about all this

Measured 330 tests across 30 files. Zero create a second user. Zero assert that one operator cannot reach another's data. The isolation category the brief ranks highest does not exist yet, which is consistent with the findings surviving this long.

The cost of onboarding a research ticker today

This is the clearest measurement of the problem the rebuild exists to fix. A per-ticker research directory holds 8 files. Six are byte-identical across every ticker. Only two carry anything ticker-specific:

  backtest.py      64 lines   identical in 13 dirs
  data.py          31 lines   identical in 16 dirs
  features.py      92 lines   identical in 15 dirs
  iterate.py      120 lines   identical in 13 dirs

So adding a ticker means copying eight files to change sixteen values. The target — one config entry, zero copied files — is not a stretch goal here; the code is already uniform enough to collapse. Data

CSV profile, against the files themselves

124 CSV files, 150,692 data rows. Almost all of it is machine state under runtime/ (114 files, 150,209 rows) that the bots recreate — that is Phase 9 deletion, not Phase 8 migration. The data that actually migrates is 424 rows in sampath's folder, and both populated files are malformed in ways an importer must handle deliberately.

v2_trade_history.csv — the header is missing a columnBlocks import

324 rows. The header declares 19 columns. 231 rows carry 20 fields. The undeclared 20th is a boolean — 220 FALSE, 11 TRUE — which by every other signal in the codebase is the dry_run flag; core/database.py:290 describes exactly this gap, that btc15 v2/v3/v4 "write paper and live rows to the same CSV with no distinguishing field".

The 93 narrow rows genuinely predate the flag, so 93 rows have an unknowable paper-or-live status from the file alone. Three declared columns — MAX_LOSS_PCT, MAX_PROFIT_PCT, ENTRY_SIGNAL — are 100% blank across all 324 rows.

trade_history_main.csv — it is an event log, not a trade tableBlocks import

99 rows, all 23 fields wide, but 54 rows have the first 18 fields blank and carry only ticker, status=CLOSED, ts_close, pv_close, realized_pnl. The other 45 are entry rows. So the file is 45 opens plus 54 close events appended separately — reading it as one-row-per-trade, which is what the row count suggests, double-counts and loses the join.

97 distinct tickers across 99 rows, so ticker alone is not a key. Three rows are still OPEN.

Four of seven files are header-onlyNote

paper_trades_main.csv, trade_history_sports.csv, v3_trade_history.csv, v4_trade_history.csv hold a header and no rows. Their column sets still differ from each other (23 / 19 / 20 / 19), which is more evidence that each bot version invented its own layout.

Other typed problems the importer must decide on: returns is a string with a percent sign ("-50.69%"), side and direction hold yes/no rather than booleans, and ts carries a trailing CST in the text while ts_epoch is a float — two representations of the same instant, disagreeing about timezone handling in exactly the way core/database.py:63 already had to correct for India signals.

Honesty

Gaps — what I could not determine

  1. What uses the shared TBOT_API_KEY. Phase 0 Decision 03 depends on this and I still cannot answer it from the code. It authenticates any request; nothing records who presents it. If a cron job, supervisor or deploy script uses it against data endpoints, demoting it breaks them. I need you to tell me, or to accept that we find out by removing it in a controlled window.
  2. Whether the 93 unflagged v2 rows are paper or live. _backfill_btc15_modes tries to infer this from bot_runs time windows. Whether that inference is trustworthy enough to carry into the new schema is a Phase 8 decision for you, not one I should make silently — these are real-money rows or they are not.
  3. Whether _test, sams and suma are real operators. sams and suma each hold a live Kalshi key and a 59-row sports history. Under scope (a) they import later, but I do not know whether they are people or test accounts.
  4. Whether the 37 uncalled client wrappers are dead or staged. Several look deliberately built and never wired up (sportsPerformance, the kill/processes family). Dead code, or a half-finished feature you intend to finish?
  5. Rules that look like accidents. The trades ledger treats unknown mode as excluded from both LIVE and PAPER views services/trades.py:42; the India timestamp correction re-runs on every boot core/database.py:63; _relocate_user_roots rewrites stored paths at startup core/database.py:171. Each is defensible and each is documented in a comment — but all three are boot-time data mutations, and I would rather name them now than inherit them by accident.
